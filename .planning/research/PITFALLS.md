# Common Pitfalls

**Analysis Date:** 2026-08-13

## Critical Pitfalls

**1. Planilha de origem sem estrutura tabular (dados "para humano ler", não "para máquina processar")**
   - **Sinais de alerta:** Células mescladas, cabeçalhos em duas linhas, uma aba por mês/ano em vez de uma tabela contínua, cores/formatação usadas como informação (ex: linha vermelha = "atrasado"), totais e subtotais misturados com dados linha a linha, campos de texto livre onde deveria haver categoria fixa (ex: "atraso na entrega", "atrasou entrega", "ATRASO ENTREGA" digitados de formas diferentes para o mesmo motivo).
   - **Estratégia de prevenção:** Antes de conectar qualquer coisa ao Power BI, auditar a planilha atual e desenhar um "modelo mínimo de captura": uma linha por evento/registro (ex: uma linha por viagem, por veículo/dia, por ocorrência), colunas fixas e padronizadas, listas suspensas (validação de dados) para campos categóricos em vez de digitação livre, e uma aba só de dados — nunca dados junto com formatação de apresentação. Se a planilha atual não suporta isso, a primeira entrega do projeto é uma planilha de captura redesenhada, não o dashboard.
   - **Qual fase deveria endereçar:** Fase de estruturação/modelagem dos dados de origem, antes de qualquer construção de visual no Power BI.

**2. KPIs sem definição operacional única (fórmula, período, dono do dado)**
   - **Sinais de alerta:** O mesmo indicador (ex: "taxa de ocupação da frota", "custo por km", "OTIF") é calculado de formas diferentes por pessoas diferentes; o gestor pergunta "de onde veio esse número?" e ninguém sabe explicar a fórmula exata; não há acordo sobre o que conta como "atraso" (tolerância de quantos minutos/horas?) ou sobre o período de referência (mês fechado, mês corrente, últimos 30 dias?); o campo que alimenta o KPI não tem um responsável claro por preenchê-lo corretamente.
   - **Estratégia de prevenção:** Antes de construir qualquer visual, documentar um "dicionário de indicadores" curto: nome do KPI, fórmula exata (numerador/denominador), fonte do dado, granularidade temporal, meta/faixa de referência (se houver) e quem é o responsável por lançar/validar o dado de origem. Validar essa definição com o próprio gestor antes de implementar — o dono do negócio precisa concordar com a fórmula, não só o analista de dados.
   - **Qual fase deveria endereçar:** Fase de definição de indicadores/requisitos, antes da modelagem no Power BI.

**3. Dashboard tecnicamente correto mas que não reflete a rotina real de decisão do gestor (baixa adoção)**
   - **Sinais de alerta:** O dashboard tem muitos gráficos "bonitos" mas o gestor continua pedindo a planilha por e-mail ou perguntando o número por WhatsApp; ninguém consegue dizer que decisão o dashboard ajuda a tomar (contratar mais veículos? cobrar motorista? renegociar frete?); o dashboard foi construído com base no que "é possível fazer com os dados", não no que o gestor realmente olha toda semana; não existe um ritual de uso (ex: reunião semanal olhando o painel).
   - **Estratégia de prevenção:** Levantar primeiro as 3-5 perguntas de gestão que o dashboard precisa responder (ex: "quais veículos estão dando prejuízo?", "quais clientes/rotas têm mais atraso?"), a partir da rotina real do gestor — não a partir dos dados disponíveis. Validar um prottipo (wireframe ou mockup simples) com o gestor antes de construir o modelo final, e definir junto com ele quando/como o painel será consultado (diário, semanal, em reunião). Preferir poucos indicadores acionáveis a muitos indicadores descritivos.
   - **Qual fase deveria endereçar:** Fase de levantamento de requisitos com o usuário final (gestor), antes e durante o design das telas do Power BI.

**4. Dependência frágil da estrutura da planilha manual (quebra silenciosa quando o formato muda)**
   - **Sinais de alerta:** O modelo do Power BI referencia células ou intervalos fixos (ex: "A2:M500") em vez de tabelas nomeadas; uma nova coluna inserida no meio da planilha, uma aba renomeada, ou uma linha de cabeçalho movida faz o relatório quebrar ou — pior — carregar dados errados sem erro visível; não existe validação de que os dados carregados batem com o esperado (contagem de linhas, soma de controle); a pessoa que alimenta a planilha não sabe quais mudanças de layout são "seguras".
   - **Estratégia de prevenção:** Usar Tabelas do Excel (Ctrl+T) nomeadas como fonte, não intervalos soltos; padronizar nomes de abas e colunas e documentar isso para quem alimenta a planilha (um "contrato de dados" simples); no Power Query, adicionar passos de validação (ex: checar que colunas esperadas existem, alertar se tipos de dado mudarem) em vez de assumir que o formato nunca muda; considerar migrar a captura para uma fonte mais estável (formulário, banco simples) assim que o volume justificar.
   - **Qual fase deveria endereçar:** Fase de construção do pipeline de dados (ETL/Power Query) e fase de handoff/documentação para quem mantém a planilha.

**5. Escopo inflado: tentar cobrir toda a operação de uma vez (frota, financeiro, manutenção, motoristas, clientes) na primeira versão**
   - **Sinais de alerta:** O projeto não sai do papel porque "falta integrar mais uma fonte"; o escopo cresce a cada conversa ("já que estamos nisso, também precisamos de..."); o primeiro dashboard entregue tem dezenas de páginas e o gestor não sabe por onde começar a olhar; tempo gasto discutindo indicadores nice-to-have supera o tempo gasto implementando os essenciais.
   - **Estratégia de prevenção:** Fechar um escopo mínimo viável com um número pequeno de KPIs essenciais (ex: 5 a 8 indicadores centrais de operação: custo por km, taxa de ocupação/utilização da frota, OTIF/atrasos, consumo de combustível, manutenção preventiva vs corretiva) ligados a uma única fonte de dados já estruturada, entregar, validar uso real por algumas semanas, e só então expandir com base no que o gestor de fato pede depois de usar. Tratar cada nova fonte de dados (financeiro, telemetria, etc.) como uma fase separada, não como parte da entrega inicial.
   - **Qual fase deveria endereçar:** Fase de definição de escopo/MVP, no início do projeto, antes de qualquer modelagem de dados.
